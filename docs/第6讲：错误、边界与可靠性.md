# 第 6 讲：错误、边界与可靠性

> 学习目标：从失败路径理解系统。能够判断问题发生在哪一层、什么信息应返回给调用方、哪些状态应被保留，以及哪些保护机制需要通过代码和测试继续验证。

可靠性不等于“从不出错”。对 TinyMCP 这类连接协议、动态插件和外部 LLM 的系统而言，更现实的目标是：失败被限制在明确边界内，被可靠地表达、记录、关联和恢复，而不会悄悄变成错误结果、资源泄漏或无限等待。

## 1. 先按边界给失败分类

一条请求从外到内会跨越多个边界：

```text
客户端
  -> 传输
  -> 协议理解
  -> 路由与能力定位
  -> 插件业务或 LLM 服务
  -> 结果返回与持久化
```

每个边界的失败含义不同。先问“失败发生在数据变成什么之前”，比先问“错误码是多少”更有效。

| 边界 | 典型失败 | 是否已定位插件或 LLM | 应给调用方什么 |
| --- | --- | --- | --- |
| 传输 | 帧不完整、连接断开、会话不存在 | 否 | 传输失败或无法送达的信号 |
| 协议理解 | JSON 不可解析、请求字段不合法 | 否 | 协议错误响应 |
| 路由与定位 | method 不支持、能力标识未登记 | 未定位具体业务 | 协议错误或明确的不可用结果 |
| 插件业务 | 外部资源不可访问、业务参数不满足 | 已定位并尝试执行 | 标记失败的业务结果 |
| LLM 服务 | 鉴权、网络、模型兼容或流式输出问题 | LLM 调用已开始 | 聊天错误事件 |
| 持久化 | 历史无法保存或恢复 | 业务可能已经完成 | 记录可观察错误，避免伪称已持久化 |

## 2. 失败如何向外表达

系统对外至少有三种不同“失败语言”，不能混用：

```text
协议错误：MCP 请求不能被正确理解或完成。
业务失败结果：请求和定位成功，但插件业务失败。
聊天错误事件：聊天流程无法继续，需要前端显示本轮失败。
```

例如，用户指定的工具名不存在，和“工具已找到但目标文件无法读取”不应表现为同一种失败：前者提示调用方修改能力标识，后者提示调用方检查业务输入或外部环境。

同样，HTTP POST 的“已接收确认”不是任何一种业务成功信号。它只说明消息已被投递给服务器。

## 3. 保护无限增长和无限等待

聊天与工具路径中，最危险的资源问题通常不是一次异常，而是持续增长或持续循环。

### 上下文增长

每轮聊天可能积累更多消息和工具结果。系统通过上下文预算、结果截断和历史摘要控制进入模型的数据量：

```text
工具输出太长
  -> 截断，并留下已截断标记

总上下文过大
  -> 压缩较早消息为摘要

仍无法在预算内继续
  -> 返回错误而不是无界增长
```

这种控制带来一个显式代价：早期原文可能不再完整可见。因此输出中应能让调用方知道发生过截断或摘要，而不是让信息消失得毫无痕迹。

### 工具循环

LLM 可能反复请求工具，或在工具失败后持续尝试。轮数上限把这种开放循环变成有限过程：

```text
轮数未到上限：继续调用 LLM 或工具。
达到上限：停止并返回错误事件。
```

这不是判断模型逻辑一定错误，而是保护服务器资源和用户等待时间。

### 外部等待

插件和 LLM 都可能依赖网络、文件系统、命令或远程服务。可靠性检查应确认每种外部调用是否具有超时、取消或失败返回路径。没有这些边界，一次请求可能长期占用连接、线程或队列。

## 4. 并发、队列与状态一致性

HTTP 模式可能同时处理多个请求和多个 SSE 会话。共享状态必须明确“谁写、谁读、何时失效”。

| 共享状态 | 需要守住的性质 | 典型保护思路 |
| --- | --- | --- |
| SSE 会话与待发送队列 | 消息不串到其他会话、入队出队有序 | 会话 ID 关联、同步保护、队列唤醒 |
| 对话历史 | 多次追加不丢失、不交叉 | 以聊天会话为单位保护 |
| 能力注册表 | 查找时不指向已销毁插件 | 生命周期顺序、受控装载和卸载 |
| 日志与持久化任务 | 业务线程不因慢磁盘长时间阻塞 | 异步队列、可观察的降级策略 |

这里的核心不是“用了锁就可靠”，而是每份共享数据都能说明它的所有者、并发访问者、可见顺序和销毁时机。

## 5. 观察、关联与恢复

出现故障时，系统需要留下足够线索回答“哪一次、哪一层、为何失败”。

### 观察

应至少观察以下事件：

```text
服务启动配置和已装载插件数量
请求进入、协议错误、能力定位和业务失败
SSE 会话建立、断开、入队和发送失败
LLM 请求开始、流式完成、工具循环轮数和上下文控制
对话历史保存与恢复结果
```

日志中的敏感输入、工具输出或密钥需要额外处理；“方便排障”不能成为泄露数据的理由。

### 关联

不同层的标识应该被保留在合适位置：

```text
请求 ID：关联协议请求和协议响应。
SSE 会话 ID：关联 HTTP 入站请求和对应出站流。
聊天会话 ID：关联历史消息和持久化记录。
工具调用 ID：关联模型提出的某次调用和对应工具结果。
```

这些标识共同构成故障追踪链，但彼此不可替换。

### 恢复

恢复策略取决于失败类型：

| 失败 | 合理的下一步 |
| --- | --- |
| 请求格式错误 | 调用方修正后重新提交 |
| 能力不存在 | 重新获取能力目录或改用正确标识 |
| 插件业务失败 | 修正业务参数、外部环境，必要时重试 |
| SSE 连接断开 | 使用会话 ID 尝试重连，并确认未送达结果的处理方式 |
| LLM 服务失败 | 检查连接和模型兼容性，避免盲目重复消耗性调用 |
| 持久化失败 | 保持内存状态的边界，记录失败并决定是否允许稍后重试 |

“重试”应是有条件的。对有副作用的 Tool，重复执行可能造成重复操作，因此需要先判断工具调用是否幂等，或由业务层提供去重标识。

## 6. 从两个失败故事复盘

### 故事一：直接工具调用找不到工具

```text
客户端提交合法 JSON-RPC 请求
  -> method 被正确路由到工具调用
  -> 注册表找不到该工具名
  -> 生成明确失败，而不是随机选择另一个插件
  -> 客户端重新获取能力目录或修正工具名
```

这说明协议层正常，失败在能力定位边界。

### 故事二：聊天循环无法继续

```text
用户消息和工具定义已送入 LLM
  -> LLM 服务失败，或循环达到上限
  -> 服务器向前端发送错误事件
  -> 不应伪造“成功完成”事件
  -> 会话历史只保存已明确完成或已明确记录的内容
```

这说明聊天前端不能只根据是否收到部分文本判断成功，必须区分增量、完成和错误事件。

## 7. 本讲需要在验证阶段核查的事项

本讲描述的是应该能从运行时观察到的可靠性边界。后续回到实现时，优先验证：

1. 各类错误是否真的按上述边界返回，而不是被吞掉或错误包装。
2. 外部调用是否都有有限等待和可诊断失败信息。
3. 多个 HTTP/SSE 请求并发时，会话和响应是否会串线。
4. 插件卸载、服务停止和连接断开时，是否留下失效引用或未清理状态。
5. 截断、摘要、轮数上限触发时，前端和日志是否能看见原因。
6. 对话保存失败时，系统是否准确表达持久化状态。

## 8. 学后自测

1. 协议错误与业务失败结果的根本区别是什么？
2. 为什么“已接收确认”不能当作工具成功？
3. 轮数上限解决了什么问题，又牺牲了什么？
4. 为什么对有副作用的工具不能无条件重试？
5. 四种 ID 各自用于关联什么？
6. 为什么连接断开可能造成“业务已完成但客户端未收到结果”？
7. 为什么记录日志时仍要关注敏感数据？
