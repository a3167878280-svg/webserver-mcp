# 第 5 讲：聊天与工具循环

> 学习目标：理解自然语言消息如何成为 LLM 上下文，LLM 如何提出工具意图，工具结果又如何回到模型，直到形成最终回答。

第 2 讲的直接 MCP 路径中，客户端已明确写出工具名和参数。聊天路径不同：用户只表达目标，是否调用工具、调用哪个工具、使用哪些参数，由 LLM 在对话过程中决定。

## 1. 聊天路径的角色分工

先把责任边界摆清楚：

```text
用户：表达问题和目标。
聊天前端：提交消息，显示流式状态。
服务器：准备上下文、协调 LLM、执行模型要求的工具。
LLM：决定直接回答，或提出工具调用意图。
插件：执行被确定的工具调用，返回业务结果。
```

最重要的原则是：**LLM 负责选择，服务器负责执行，插件负责实现。**

LLM 不直接接触文件系统、命令或网络能力；它只看到工具定义，并以结构化意图请求服务器代为执行。

## 2. 聊天请求进入后，先构建上下文

聊天前端提交的内容可抽象为：

```text
用户消息
可选聊天会话 ID
可选已有历史
模型连接信息
可选禁用工具列表
```

服务器把它们组合为 LLM 能理解的上下文：

```text
既有消息历史
  + 系统消息
  + 当前用户消息
  + 当前可用工具定义
  -> 本轮 LLM 请求
```

系统消息用于设定整体行为边界，例如语言、回答风格和工具使用倾向。工具定义来自同一份能力注册表，但聊天请求可以从工具清单中剔除用户禁用的项目。禁用工具只影响本轮提供给 LLM 的“可选项”，不改变服务器已登记的能力目录。

如果请求绑定聊天会话，当前用户消息和后续完成结果可被保存到该会话历史；如果没有绑定，历史只存在于当前请求提供的上下文中。

## 3. 第一次 LLM 返回：文本、工具意图，或错误

LLM 使用流式方式输出。服务器不会等到完整回答才通知前端，而是把可见文本增量逐段转发，使界面能逐步显示回答。

LLM 的一次返回有三种关键形态：

| 形态 | 含义 | 下一步 |
| --- | --- | --- |
| 只有文本增量 | 模型认为不需要工具 | 完成本轮回答 |
| 工具调用意图 | 模型希望服务器执行一个或多个工具 | 进入工具循环 |
| 连接或格式错误 | 模型服务不可用，或输出无法使用 | 向前端发送错误事件 |

工具调用意图至少包含：工具调用 ID、工具名和参数文本。流式协议可能把这些字段拆成多个片段送达，因此服务器需要先累积，确认工具名和参数完整后才能执行。

## 4. 工具循环：模型提出，服务器执行，再交回模型

工具循环是聊天路径的核心。它可以用下面的循环表达：

```text
向 LLM 发送当前上下文和工具定义
  -> LLM 返回文本，或工具调用意图

若没有工具意图：结束，文本成为最终回答

若有工具意图：
  -> 记录模型提出的工具调用消息
  -> 逐个执行工具
  -> 将每个工具结果追加为 tool 消息
  -> 带着更新后的上下文再次请求 LLM
```

其中“执行工具”并不是另写一套逻辑，而是再次进入第 2 讲的能力执行主干：

```text
工具调用意图 { 工具名, 参数文本 }
  -> 转成结构化参数
  -> 按 tools/call 的语义定位插件
  -> 插件执行
  -> 统一工具结果
```

这样设计的好处是：直接 MCP 客户端和聊天路径对同一个工具得到同一类执行行为、相同的插件边界和相同的错误语义。

### 一轮中有多个工具时

一个模型返回中可以包含多个工具意图。系统逐个执行，并为每个工具调用保留对应的工具调用 ID。结果作为独立 tool 消息加入历史，下一次 LLM 请求才能把“哪个结果对应哪个调用”重新关联起来。

```text
assistant 消息：提出 call-A、call-B
tool 消息 1：携带 call-A 的结果
tool 消息 2：携带 call-B 的结果
下一轮 LLM：同时看到提出的调用和每个对应结果
```

## 5. 上下文为什么必须被管理

每一轮都会新增用户消息、模型文本、工具调用记录和工具结果。若无控制，多轮对话或大体积工具输出会超过模型的上下文窗口。

因此，聊天路径有三类上下文控制：

```text
单次工具结果过长
  -> 截断到预算内，并保留截断提示

总历史接近模型上下文上限
  -> 将较早部分压缩为摘要，保留近期细节

工具调用轮数持续增加
  -> 达到上限后停止循环并返回错误
```

这三类控制的本质都是限制“进入下一次 LLM 请求的数据量和循环次数”。它们追求的是让对话可继续，而不是保证模型永远保留全部原始细节。

## 6. 前端在聊天期间看到什么

聊天路径的出站不是 JSON-RPC 响应，而是当前聊天 HTTP 连接上的流式事件。前端会依次看到类似状态：

```text
文本增量：模型正在生成可见回答。
工具开始：模型决定使用某项工具。
工具结果：工具执行结束，得到结构化结果。
完成：模型已给出最终回答。
错误：模型连接、工具循环或请求处理无法继续。
```

这些事件描述“本次对话正在发生什么”，而不是第 3 讲中的 MCP 协议响应。二者都可采用 SSE 技术，但携带的数据语义不同：

| 流 | 主要数据 | 关联方式 |
| --- | --- | --- |
| MCP HTTP+SSE 流 | JSON-RPC 协议响应 | SSE 会话 ID + 请求 ID |
| 聊天流 | 文本增量、工具状态、最终回答 | 当前聊天 HTTP 连接 + 可选聊天会话 |

## 7. 一次“需要工具”的聊天时序

```text
用户：提出自然语言问题
  -> 前端提交聊天请求
  -> 服务器组装历史、系统消息和可用工具
  -> LLM 流式输出，并提出工具意图
  -> 前端收到文本增量和工具开始状态
  -> 服务器调用对应插件
  -> 前端收到工具结果状态
  -> 工具结果追加到 LLM 上下文
  -> 服务器再次请求 LLM
  -> LLM 根据工具结果生成最终文本
  -> 前端收到完成事件
  -> 可选保存用户消息、工具结果和最终回复
```

如果 LLM 在第一次返回时没有工具意图，中间“插件执行”和“再次请求 LLM”两段会被跳过。

## 8. 学后自测

1. 为什么聊天路径需要把工具定义一并交给 LLM？
2. 禁用工具列表影响的是插件目录，还是本轮提供给 LLM 的工具清单？
3. 工具调用意图和工具结果分别由谁产生？
4. 为什么工具结果必须带回下一轮 LLM 上下文？
5. 为什么模型提出工具调用后，仍不能由模型自己直接执行？
6. 为什么工具调用 ID 在一轮多个工具时很重要？
7. 为什么聊天流和 MCP HTTP+SSE 流不能按相同语义理解？
8. 上下文截断、摘要和轮数上限分别限制了什么？
