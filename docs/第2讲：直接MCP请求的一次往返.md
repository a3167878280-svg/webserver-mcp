# 第 2 讲：直接 MCP 请求的一次往返

> 学习目标：跟踪一条已经完整到达服务器的 MCP 请求，理解它如何从 JSON 文本变成能力调用，并最终成为带关联标识的响应。

本讲从第 1 讲的“服务器已经就绪”开始。我们暂时不关心消息通过 stdio 还是 HTTP 抵达，也不讨论聊天用户和 LLM；只研究共同的协议主干。

## 这一讲要回答的问题

一条客户端消息进入服务器后，系统如何回答下面四个问题？

```text
这是不是一条合法的协议请求？
它想让服务器做什么？
如果要使用能力，应交给哪个插件？
结果或错误该如何回到原来的请求方？
```

本讲结束时，你应能用一条 `tools/call` 请求解释完整的数据变化，也能区分“协议层失败”和“工具业务失败”。

## 1. 先确定范围：什么是直接 MCP 请求

直接 MCP 请求来自已经了解 MCP 协议的客户端。客户端不必使用自然语言，也不需要 LLM 帮它决定工具；它直接说明自己想做的协议动作。

下面是一个抽象请求：

```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "某个工具",
    "arguments": {
      "某个参数": "某个值"
    }
  }
}
```

它表达的不是“请帮我解决问题”，而是一个明确指令：使用给定参数调用某个已登记工具，并把结果对应回请求 `42`。

一条直接 MCP 请求可以走向四个大分支：

```text
无法理解文本或不符合协议
  -> 协议错误响应

方法不存在
  -> 协议错误响应

方法存在，但找不到能力或执行过程出错
  -> 错误结果或协议错误响应

方法与能力都有效
  -> 成功协议响应
```

## 2. 总流程：从 JSON 文本到 JSON 响应

直接 MCP 请求的共同主干可以先压缩为六步：

```text
完整 JSON 文本
  -> 解析与基本校验
  -> 结构化协议请求
  -> 按 method 路由
  -> 业务结果或错误
  -> 结构化协议响应
  -> JSON 响应文本
```

其中最重要的边界是：

```text
传输层只负责交付完整 JSON 文本。
协议层负责理解和路由该文本。
插件层负责执行已定位的业务能力。
```

因此，能力调用从来不是“JSON 直接进入插件”。中间必须经过协议校验、方法路由和能力定位三道边界。

## 3. 第一步：解析与基本校验

服务器收到的起点是一段 JSON 文本。它需要先被转化为结构化协议请求，至少读出以下字段：

| 字段 | 表示什么 | 后续由谁使用 |
| --- | --- | --- |
| `jsonrpc` | 协议版本 | 协议层确认消息是否属于当前约定 |
| `id` | 请求 ID | 响应层把结果匹配回原请求 |
| `method` | 请求要执行的协议动作 | 路由层选择处理分支 |
| `params` | 该动作的输入数据 | 相应业务分支和插件 |

数据变化如下：

```text
JSON 文本
  -> JSON 数据
  -> 协议请求 { 版本, 请求 ID, method, params }
```

这里的失败发生在“尚未知道要调用哪个能力”之前：

- JSON 文本本身不能被解析。
- 协议版本不正确。
- `method` 缺失或不是文本。

这些情况属于**协议理解失败**。服务器不能可靠地进入业务层，只能生成规范的协议错误响应。此时插件不会被访问，能力注册表也不会被查询。

### 通知：没有响应的合法消息

如果请求没有 `id`，它是一个**通知**。通知仍需要被解析、校验和路由，只是客户端明确表示自己不等待回应。

```text
通知
  -> 正常执行业务动作
  -> 不创建协议响应
  -> 不通过传输通道回传内容
```

这与“请求失败后没有响应”完全不同。前者是协议约定，后者是异常或连接问题。

## 4. 第二步：按 method 路由

结构化请求出现后，服务器不立即查插件，而是先根据 `method` 选择 MCP 业务动作。可以把路由器看成一张“方法名到处理规则”的目录。

本项目的常见动作分成四组：

| 动作组 | 目的 | 是否通常需要定位插件 |
| --- | --- | --- |
| 初始化与心跳 | 建立协议关系、确认服务存活 | 否 |
| 能力列举 | 返回当前可发现的工具、资源或提示模板 | 是，读取注册表中的目录 |
| 能力使用 | 调用工具、读取资源、取得提示模板 | 是，定位一个具体插件 |
| 初始化完成通知 | 告诉服务客户端已准备好 | 否，且不返回响应 |

此阶段的关键数据变化是：

```text
{ method, params }
  -> 某个业务分支 + 该分支需要的输入
```

如果 `method` 不在路由目录中，服务器已经知道这是一条合法 JSON-RPC 请求，但不知道该执行哪个 MCP 动作。因此会产生“方法不存在”的协议错误。它与 JSON 解析失败不同：前者看懂了请求结构，只是不支持该动作。

## 5. 第三步：三种能力动作如何使用注册表

第 1 讲中，插件启动后已将能力登记进注册表。现在请求到来，注册表才开始发挥“从名字找到所属插件”的作用。

### A. 列举能力：从索引到能力目录

当客户端请求列出工具、资源或提示模板时，服务器不执行具体业务，而是读取已登记的能力定义并组成目录：

```text
注册表中的若干能力索引
  -> 工具 / 资源 / 提示模板定义集合
  -> 客户端可发现的能力目录
```

这里返回的是元数据，例如名称、用途说明、参数结构或资源 URI，不是文件内容、天气结果或命令输出。

### B. 调用工具：从工具名到工具结果

工具调用需要从 `params` 中取出两项数据：工具名和工具参数。数据流如下：

```text
{ 工具名, 工具参数 }
  -> 注册表查找
  -> 所属插件实例
  -> 插件执行业务
  -> 工具结果 { 内容, 是否失败 }
```

“工具不存在”和“工具执行失败”必须分开：

| 情形 | 发生在哪一层 | 含义 |
| --- | --- | --- |
| 工具名未登记 | 能力定位 | 注册表找不到所属插件，无法开始调用 |
| 工具返回失败结果 | 插件业务 | 找到了插件，也开始执行了，但业务条件不满足或外部操作失败 |

第一个问题意味着协议动作无法完成；第二个问题意味着协议调用本身完成了，只是业务结果标记为失败。客户端可据此决定是修改请求、提示用户，还是重试。

### C. 读取资源与取得提示模板：从标识到内容

资源读取和提示模板获取沿用完全相同的定位思想，只是查找键和返回形态不同：

```text
资源 URI
  -> 注册表
  -> 所属插件
  -> 资源内容

提示模板名 + 模板参数
  -> 注册表
  -> 所属插件
  -> 预设消息集合
```

Resource 重点是“读取某个可发现的数据”；Prompt 重点是“产生一组为对话准备的消息”。它们都不等同于执行 Tool。

## 6. 第四步：结果、异常与协议响应

业务分支结束后，服务器需要把不同来源的结果收敛成统一的协议响应。请求 ID 在这里重新出现：只要原请求不是通知，响应就会携带同一个 ID。

```text
业务成功结果
  -> { jsonrpc, id, result }

协议层或处理层错误
  -> { jsonrpc, id, error }
```

`result` 和 `error` 是互斥的。一个响应不能既说调用成功又同时给出协议错误。

可以按错误来源理解响应：

| 错误来源 | 典型问题 | 响应表达 |
| --- | --- | --- |
| 文本解析 | 不是 JSON 或结构无法读取 | 解析错误 |
| 协议校验 | 版本或必要字段不符合约定 | 无效请求错误 |
| 方法路由 | method 未被支持 | 方法不存在错误 |
| 参数或内部处理 | 参数无法使用，或处理过程抛出异常 | 参数错误或内部错误 |
| 插件业务 | 文件不可读、外部服务不可用等 | 通常作为业务结果的失败状态 |

最实用的判断方式是问：**服务器是否已经成功理解请求，并且定位到要执行的业务？**

- 若没有，倾向于协议错误。
- 若已经定位并执行，但业务本身失败，倾向于返回标记失败的业务结果。

## 7. 一次工具调用的完整数据追踪

现在把上面的阶段串成一次完整示例。假设客户端已经知道一个工具名，并希望传入参数执行它：

```text
1. 客户端发送 JSON 文本
   { 版本, id=42, method=tools/call, params={ 工具名, 参数 } }

2. 协议层解析文本
   JSON 文本 -> 结构化协议请求

3. 路由层识别 method
   tools/call -> 工具调用业务分支

4. 调用分支提取业务输入
   params -> { 工具名, 工具参数 }

5. 注册表定位能力所有者
   工具名 -> 插件实例

6. 插件执行
   工具参数 -> 业务工作 -> 工具结果

7. 协议层包装结果
   工具结果 -> 协议响应 { id=42, result=... }

8. 传输层返回文本
   协议响应 -> JSON 文本 -> 原客户端
```

注意两次“形状变化”：

```text
第一次：JSON 文本变成结构化协议请求，以便服务器理解它。
第二次：业务结果变成 JSON 响应文本，以便客户端理解它。
```

插件只参与第 5、6 步。让插件不直接处理原始传输文本，是为了使它不依赖客户端来自 stdio 还是 HTTP，也不需要理解请求 ID、错误码等协议细节。

## 8. 学后自测

1. 为什么 `method` 合法并不代表工具一定存在？
2. “工具不存在”和“工具执行失败”分别发生在哪个阶段？
3. 为什么列举工具不会执行任何具体工具逻辑？
4. 一条通知与普通请求相比，少了哪一步？
5. 请求 ID 从进入服务器到返回客户端，经历了怎样的变化？
6. 如果 JSON 文本无法解析，为什么不应尝试查询能力注册表？
7. 为什么 Tool、Resource 和 Prompt 都需要先经过注册表？
