# 第 7 讲：回到代码验证模型

> 学习目标：把前 6 讲的运行时模型转化为高效的代码阅读、测试和排障方法。目标不是从头逐行读完项目，而是让每段实现都能在已有流程图中找到位置。

到这一讲，你已经有一张系统地图：启动、直接 MCP 请求、传输方式、插件契约、聊天循环、错误边界。现在才适合进入实现细节，因为你已知道要验证什么，而不是在大量细节中寻找主线。

## 1. 验证原则：先问四个问题

阅读任一模块时，先用同一组问题定位它：

```text
输入是什么？
输出是什么？
它依赖哪些长期或按需状态？
出错后把控制权和数据交给谁？
```

如果一个模块无法用这四句话说明，它往往还没有被放进正确的运行时位置。此时不要继续深挖局部语句，应先回到前六讲的流程图重新定位。

## 2. 按数据流而不是目录阅读

建议按照以下顺序验证，而不是按文件夹顺序通读：

```text
启动入口
  -> 配置与长期对象
  -> 插件装载与能力登记
  -> 传输入口
  -> 协议解析、路由、响应包装
  -> 注册表与插件执行
  -> HTTP/SSE 会话发送
  -> 聊天编排、LLM 调用与历史管理
  -> 错误处理、日志、测试
```

这样阅读时，每一步都回答一个前一讲已经提出的问题：

| 阅读对象 | 重点验证的模型 |
| --- | --- |
| 启动入口 | 第 1 讲的四个启动阶段是否依序发生 |
| 传输实现 | 第 3 讲的消息边界、会话关联和异步返回是否成立 |
| 协议实现 | 第 2 讲的解析、路由、通知和错误分支是否成立 |
| 插件接口与示例插件 | 第 4 讲的契约、三类能力和生命周期是否成立 |
| 聊天编排 | 第 5 讲的上下文、工具循环和流式事件是否成立 |
| 日志、持久化、停止逻辑 | 第 6 讲的可观察性、恢复和清理边界是否成立 |

## 3. 每条路径只做一次“纵向追踪”

不要一开始同时理解所有分支。先选一个最小成功案例，沿着它从入口走到出口；再刻意走一次失败案例。

### 路径 A：直接 MCP 工具调用

建议追踪的问题：

```text
完整请求文本在哪里第一次成为结构化数据？
method 在哪里被选择为工具调用？
工具名在哪里变成所属插件？
工具结果在哪里变成协议响应？
响应最终如何返回客户端？
```

然后补一个失败案例：不存在的工具名。目标是看到“解析成功、路由成功、定位失败、错误返回”的边界，而不是只看成功路径。

### 路径 B：HTTP+SSE 会话

建议追踪的问题：

```text
会话 ID 在何时生成或恢复？
POST 请求如何关联当前会话？
协议响应在哪里进入待发送队列？
哪一段从队列取出并写成 SSE 事件？
连接断开后，哪些状态仍保留，哪些状态结束？
```

### 路径 C：聊天工具循环

建议追踪的问题：

```text
用户消息、历史、系统消息和工具定义怎样拼成 LLM 请求？
流式文本和工具意图如何分别被处理？
工具意图怎样重新接入直接 MCP 的执行主干？
工具结果怎样写回模型上下文和可选对话历史？
完成、错误和轮数上限如何终止本轮？
```

## 4. 让测试成为行为合同

测试不应只是“运行成功”，而应固定前几讲的关键承诺。可以先按下面的行为矩阵检查现有测试覆盖，再补最小缺口：

| 行为 | 最小验证 | 主要证明什么 |
| --- | --- | --- |
| 正常协议解析 | 合法请求能读出版本、ID、方法和参数 | 第 2 讲的入口边界 |
| 非法协议 | 无法解析、版本错误、方法错误能得到正确失败 | 错误不会误入插件 |
| 通知 | 无 ID 请求不产生响应 | 协议语义正确 |
| 能力列举 | 已登记能力能出现在目录中 | 第 1、4 讲的注册结果可发现 |
| 能力调用 | 名称能定位插件并返回统一结果 | 第 2、4 讲的主干 |
| 资源与提示模板 | URI 或模板名能定位所属插件 | 三类能力的边界 |
| stdio 帧 | 多条连续消息不串包 | 第 3 讲的消息边界 |
| HTTP/SSE | 结果进入正确会话流 | 会话隔离与异步返回 |
| 聊天循环 | 工具意图能带着工具结果进入下一轮 | 第 5 讲的循环 |
| 上下文限制 | 大结果被截断或压缩且可观察 | 第 6 讲的资源保护 |

测试有三种价值：

```text
单元测试：固定一个小模块的输入输出。
集成测试：确认多个边界拼接后的完整路径。
回归测试：防止一次修改破坏已理解的行为合同。
```

## 5. 运行观察：让流程图与真实进程对齐

当阅读不能确定真实行为时，优先运行最小案例并观察日志或前端事件。每次观察只验证一个假设：

```text
“插件是否在启动时被登记？”
“通知是否真的没有响应？”
“HTTP POST 的结果是否经 SSE 而非 POST 返回？”
“工具结果是否真的进入下一轮 LLM 上下文？”
```

避免在一次运行中同时验证全部功能。否则看到一段长日志后，仍无法判断哪一个边界成立或失效。

对每个观察案例，记录四项：

```text
输入：提交了什么消息或操作。
期望：根据流程图应发生什么。
证据：实际收到的响应、事件或日志。
结论：模型被确认、被修正，还是仍需继续追踪。
```

## 6. 阅读实现时的“反向提问”

当你看到一段实现，可以反向用它挑战现有模型：

| 看到的现象 | 应提出的问题 |
| --- | --- |
| 新增一个缓存或队列 | 谁写入、谁读取、满了或断开时怎样处理？ |
| 新增一个 ID | 它与请求 ID、SSE 会话 ID、聊天会话 ID、工具调用 ID 有何不同？ |
| 新增一个错误分支 | 它属于协议错误、业务失败还是聊天错误事件？ |
| 新增一个插件能力 | 它为何是 Tool、Resource 或 Prompt，而不是另外两类？ |
| 新增一次外部调用 | 超时、重试、幂等性和敏感数据如何处理？ |
| 新增一段历史数据 | 它何时保存、何时恢复、是否进入 LLM 上下文？ |

这能避免“代码看懂了，但系统没看懂”的常见问题。

## 7. 建议的实战节奏

完成这一轮学习后，可以按四次短会话巩固：

1. 用 30 分钟验证启动和插件目录，更新第 1、4 讲的状态图。
2. 用 45 分钟验证一条成功和一条失败的直接 MCP 调用，更新第 2 讲的错误表。
3. 用 45 分钟观察同一调用在 stdio 与 HTTP+SSE 下的出入站差异，更新第 3 讲的时序图。
4. 用 60 分钟观察一次需要工具的聊天循环，记录上下文、事件序列和最终历史。

每次只写下一个“已确认事实”和一个“待验证问题”。这比一次性写长篇源码笔记更容易保持模型与实际行为一致。

## 8. 学后自测

1. 为什么阅读项目入口后不应立刻跳到任意插件业务实现？
2. 如果一个测试失败，怎样判断它违背了哪一讲的模型？
3. 为什么一个最小成功案例之后还必须追踪一个失败案例？
4. 如何证明一个 HTTP MCP 响应实际通过 SSE 返回？
5. 新增一个 ID 时，最先应该问哪两个问题？
6. 单元测试、集成测试和回归测试各自固定什么？
7. 为什么运行观察应一次只验证一个假设？
