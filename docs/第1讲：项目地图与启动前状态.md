# 第 1 讲：项目地图与启动前状态

> 学习目标：不追踪任何一条用户请求，只理解 TinyMCP 启动后为何已经具备服务能力，以及哪些状态会在后续请求中被反复使用。

## 这一讲要回答的问题

服务器刚启动时，还没有客户端请求、也没有用户对话。此时它究竟做了什么准备，才能在之后正确处理不同客户端的消息？

本讲结束时，你应该能自己解释：

```text
配置从哪里来？
能力从哪里来？
谁记住“某个能力由谁执行”？
哪些状态会一直活到服务器退出？
服务器什么时候才算真正准备好接收请求？
```

## 1. 启动前：项目处于什么状态

启动前，磁盘上已经存在两类静态输入：

```text
运行配置：决定服务以什么方式对外提供、在哪个端口监听、去哪里找插件、默认连接哪个 LLM。

插件库：每个插件库中封装一组实际能力，并能说明自己公开哪些工具、资源和提示模板。
```

它们都只是文件，不是内存中的可用服务。特别要注意：插件目录里即使有很多插件库，客户端此时仍不能列出或调用任何能力，因为服务器还没有把它们装进当前进程，也没有建立可检索的能力目录。

可以把启动前的状态画成：

```text
磁盘
├── 配置文件
└── 插件目录
    ├── 插件库 A
    ├── 插件库 B
    └── 插件库 C

内存
└── 尚未运行的服务器：没有配置对象、没有插件实例、没有能力索引、没有会话
```

## 2. 启动主线：四个阶段

把启动过程先记成下面四步。细节暂时不重要，先抓住每步产生了什么新状态。

```text
读取配置
  -> 建立基础运行环境
  -> 装载插件并登记能力
  -> 选择传输方式，进入等待
```

### 阶段一：读取配置

服务器将配置文件转换为运行时配置。这个配置不只是“启动参数”，而是后续多个角色共享的决策依据。

配置至少影响以下问题：

| 决策 | 影响的运行时行为 |
| --- | --- |
| 服务模式 | 使用本地标准输入输出，还是启动 HTTP 服务 |
| 监听端口 | HTTP 服务对外暴露的位置 |
| 插件目录 | 去哪里发现可装载的插件库 |
| 日志策略 | 是否记录、以什么方式保存运行过程 |
| 默认 LLM 连接信息 | 聊天路径未显式指定时使用的模型服务地址和模型名 |

数据变化是：

```text
配置文件中的文本
  -> 经过读取和校验
  -> 运行时配置
```

如果配置不存在或无法正确解析，系统会退回一组默认值。因此“服务器能启动”不必然意味着“它使用了你期望的配置”。这是一条后续排查问题时很重要的边界。

### 阶段二：建立基础运行环境

在开始接收外部消息前，服务器会先准备全局运行条件：日志、退出信号处理，以及管理插件和会话的长期对象。

这一阶段的重点不是业务能力，而是让服务具备可观察、可停止、可管理的基础条件：

```text
运行配置
  -> 日志可记录
  -> 停止信号可被识别
  -> 插件管理器已存在
  -> 能力注册表已存在但为空
  -> 对话管理器已存在，等待需要时创建或恢复会话
```

此时最容易混淆的是“管理器存在”和“它管理的数据已经存在”。例如，对话管理器可以在服务启动时就存在，但真实对话历史只会在已有持久化记录被恢复，或用户首次创建、使用某个会话后才出现。

### 阶段三：装载插件并登记能力

这是启动阶段最关键的业务准备。服务器扫描配置指定的插件目录，逐个尝试装载可识别的动态插件库。

一个插件成功加入运行时，需要经历下面的概念过程：

```text
插件库
  -> 被装入服务器进程
  -> 产生插件实例
  -> 申报它提供的能力定义
  -> 能力定义写入注册表索引
```

插件申报的能力分为三种：

| 类型 | 启动时登记什么 | 后续怎样使用 |
| --- | --- | --- |
| Tool | 工具名、说明、参数结构 | 客户端或 LLM 用名称和参数请求执行 |
| Resource | 资源 URI、说明、内容类型 | 客户端先发现，再按 URI 读取 |
| Prompt | 模板名、说明、所需参数 | 用户选择模板并填入参数，得到预设消息 |

注册表形成的不是“能力结果”，而是“能力路由目录”。它只记住：某个名字或 URI 对应哪个插件实例，以及该能力的描述是什么。

```text
工具名       -> 所属插件 + 工具定义
资源 URI     -> 所属插件 + 资源定义
提示模板名   -> 所属插件 + 模板定义
```

因此，插件的实际业务逻辑还没有执行。启动阶段只完成了发现和登记；真正的文件读取、网络访问或命令执行，要等后续请求到来时才发生。

如果两个插件声明了相同的名字或 URI，先成功登记的能力会保留，后来的冲突声明不会覆盖它。这样保证一次请求仍有确定的去向，但也意味着插件装载顺序可能影响最终暴露的能力集合。

### 阶段四：选择传输方式，进入等待

完成能力登记后，服务器创建传输通道，并把“收到完整消息后要交给上层”的处理规则接入通道。

运行配置决定两种服务形态之一：

```text
stdio 模式：进程等待标准输入中的协议消息，并把响应写到标准输出。

HTTP 模式：进程启动 HTTP 服务，等待 HTTP 请求；同时提供 SSE 流，用于异步推送响应和聊天事件。
```

无论哪种模式，服务器此时已经持有相同的核心长期状态：运行时配置、插件实例和能力注册表。区别只在于外部消息抵达的方式，以及处理完成后的结果如何送回。

到达这个阶段，服务器才算“准备就绪”：它还没有处理任何业务请求，却已经能回答“我有哪些能力”，也已经知道每一项能力应该交给谁。

## 3. 启动后的状态快照

当服务器进入等待状态时，可以用下面的快照理解整个内存世界：

```text
TinyMCP 运行时
├── 运行时配置
│   ├── 服务模式与端口
│   ├── 插件目录
│   ├── 日志策略
│   └── 默认 LLM 连接信息
├── 基础服务
│   ├── 日志系统
│   └── 停止控制
├── 插件系统
│   ├── 已装载的插件实例
│   └── 能力注册表
│       ├── 工具索引
│       ├── 资源索引
│       └── 提示模板索引
├── 对话系统
│   └── 已恢复或新建的会话历史（可能为空）
└── 传输系统
    └── 正在等待外部消息的通道
```

把这些状态分成两类会更容易理解：

| 类别 | 包含什么 | 何时变化 |
| --- | --- | --- |
| 长期基础状态 | 配置、日志、插件实例、能力索引、传输通道 | 启动时创建，通常持续到停止 |
| 按需业务状态 | 一次请求、一次响应、SSE 会话、聊天历史、工具结果 | 有请求或会话活动时创建和更新 |

第 2 讲会跟踪第一类按需状态中的“协议请求与响应”；第 3 讲会把 SSE 会话展开；第 5 讲才会完整讨论聊天历史和工具结果。

## 4. 这一讲最重要的因果关系

下面四条关系应能直接复述：

```text
没有运行时配置，服务器不知道用什么方式启动，也不知道去哪里找插件。

没有成功装载的插件实例，能力只停留在磁盘上的代码，不能被执行。

没有能力注册表，服务器虽有插件，却无法按工具名或 URI 快速找到应执行的插件。

没有传输通道，服务器虽已具备能力，也没有任何入口能接收客户端消息。
```

可以把它们合成一句话：**配置决定启动策略，插件提供能力，注册表把能力变成可寻址目录，传输通道让外界能够使用这张目录。**

## 5. 学后自测

先不看源码，尝试用自己的话回答：

1. 为什么“插件文件存在于目录中”不等于“客户端已经可以调用它”？
2. 服务启动完成后，注册表里存的是工具执行结果，还是工具到插件的对应关系？
3. Tool、Resource 和 Prompt 在启动时各自登记的内容有什么不同？
4. 如果配置文件解析失败，为什么仍可能看到服务器运行起来？
5. HTTP 模式和 stdio 模式在启动完成后的共同状态是什么？又各自多了什么？
6. 为什么会话管理器可以存在，但当前没有任何对话历史？
