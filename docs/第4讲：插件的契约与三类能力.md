# 第 4 讲：插件的契约与三类能力

> 学习目标：理解插件为什么能被主程序替换和扩展，掌握 Tool、Resource、Prompt 三类能力的边界，并能从数据流判断一项需求应设计成哪一类能力。

前 3 讲已经建立了主干：服务器启动时登记能力，请求到来时按名称或 URI 找到所属插件。本讲进一步回答一个关键问题：主程序和插件彼此不了解内部实现时，它们靠什么协作？

## 1. 插件的本质：一份可执行的能力契约

插件不是“放在目录里的任意代码”，而是遵守统一能力契约的独立模块。主程序只需要知道三件事：

```text
插件是谁：名称和版本等身份信息。
插件提供什么：可发现的能力定义。
插件如何被使用：给定标识和结构化输入后，返回统一形状的结果。
```

它不需要预先知道插件内部是读取文件、访问网络、执行命令还是进行代码分析。

这份契约把系统分为两个责任域：

| 责任域 | 负责什么 | 不应该负责什么 |
| --- | --- | --- |
| 主程序 | 装载插件、登记能力、定位能力、统一协议包装 | 具体业务规则 |
| 插件 | 声明自己拥有的能力、校验业务输入、执行业务、返回业务结果 | 传输分帧、请求 ID、JSON-RPC 路由 |

因此，插件能在不改动协议主干的前提下增加能力，前提是它仍遵守同一个输入输出契约。

## 2. 插件的完整生命周期

第 1 讲见过启动时的装载。本节把整个生命周期补全：

```text
磁盘上的插件库
  -> 动态装载
  -> 创建插件实例
  -> 读取能力定义
  -> 注册能力索引
  -> 被请求多次定位和调用
  -> 注销能力索引
  -> 销毁插件实例
  -> 卸载插件库
```

### 启动时：声明，而不是执行

插件第一次被装入时，只提供能力的描述信息：

```text
Tool：名称、说明、参数结构
Resource：URI、说明、内容类型
Prompt：名称、说明、参数说明
```

这些数据被写入注册表，构成客户端可发现的能力目录。这里不会执行实际业务，也不会产生工具结果。

### 运行时：定位后，才把业务输入交给插件

请求进入协议主干并被路由后，注册表用能力标识找到插件实例。插件收到的已经是结构化业务数据：

```text
Tool：工具名 + 工具参数
Resource：资源 URI
Prompt：模板名 + 模板参数
```

插件返回的是对应类型的统一业务结果，而不是原始传输字节或完整 JSON-RPC 响应。随后协议层负责把它包装并返回客户端。

### 停止时：先让目录失效，再销毁对象

插件停止使用时，正确的顺序是：

```text
从能力注册表删除该插件的所有索引
  -> 销毁插件实例
  -> 卸载插件库
```

先注销索引的目的，是避免后续请求仍通过旧名称找到已经失效的实例。这是“所有权”和“可寻址性”分离时必须守住的顺序。

## 3. 三类能力：相同的插件系统，不同的交互语义

Tool、Resource、Prompt 都由插件申报、由注册表定位，但它们解决的问题不同。

| 类型 | 调用者的意图 | 输入 | 返回 | 是否执行动作 |
| --- | --- | --- | --- | --- |
| Tool | “请帮我做这件事” | 名称和业务参数 | 工具结果 | 是 |
| Resource | “请给我这个已公开数据” | URI | 资源内容 | 通常是读取 |
| Prompt | “请为这个对话生成预设消息” | 模板名和参数 | 消息集合 | 否，不直接执行业务 |

### Tool：主动执行的能力

Tool 适合由调用者主动发起的操作，例如查询、读取、分析或命令执行。它的核心数据流是：

```text
工具定义告诉调用者需要什么参数
  -> 调用者提交工具名和参数
  -> 插件执行
  -> 返回内容 + 成功或失败状态
```

Tool 的“参数结构”是调用者与插件之间最重要的约定。结构应该足以表达业务需求，也应让调用者在执行前知道必填项、类型和预期含义。

### Resource：可发现、可读取的数据

Resource 适合服务器主动声明“我有这些数据可供读取”。调用者先通过目录发现 URI，再单独请求内容：

```text
资源定义 { URI, 描述, 内容类型 }
  -> 客户端浏览并选择 URI
  -> 插件按 URI 提供资源内容
```

与 Tool 相比，Resource 强调稳定的“数据地址”和浏览发现，不要求调用者先构造一次业务动作。它并不意味着数据一定是永远不变的，只是交互语义是“读取已公开资源”。

### Prompt：面向对话的可复用起点

Prompt 适合将常见对话意图固化成稳定模板。调用者选择模板、填入参数，插件返回一组预设消息：

```text
提示模板定义 { 模板名, 参数说明 }
  -> 用户或客户端填写模板参数
  -> 插件生成预设消息集合
  -> 交给对话系统或 LLM 使用
```

Prompt 不是 Tool 的快捷别名。它的产物是“如何开始或约束一次对话”的消息，不是一次业务执行结果；模型随后是否调用工具是另一层决定。

## 4. 一致性来自哪里

不同插件的业务可以完全不同，但它们应在以下边界上保持一致：

| 边界 | 一致性要求 | 带来的好处 |
| --- | --- | --- |
| 身份 | 插件有稳定名称和版本 | 日志、排障和兼容性判断更清晰 |
| 发现 | 能力有唯一标识和元数据 | 客户端与 LLM 能预先了解可用能力 |
| 输入 | 参数采用结构化数据 | 调用方不必猜测字符串格式 |
| 输出 | 返回统一结果形状和失败状态 | 协议层、聊天层可用同一种方式处理 |
| 生命周期 | 注销先于销毁 | 注册表不会指向失效实例 |

其中“统一输出”不表示所有插件都要返回同样的业务文本；它表示外层有稳定容器来承载不同文本、内容类型或错误状态。

## 5. 用一个需求练习能力分类

假设要为“项目说明”增加功能，可以有三种不同设计，分别满足不同意图：

```text
Tool：根据指定目录即时生成项目说明摘要。
Resource：公开当前项目的固定说明文档 URI。
Prompt：生成一段引导 LLM 评估项目说明完整性的预设提问。
```

判断方法不是看它们是否都与“项目说明”有关，而是问：

```text
调用者期待执行一次动作吗？              -> Tool
调用者期待浏览和读取已公开数据吗？        -> Resource
调用者期待拿到一组对话引导消息吗？        -> Prompt
```

把一种能力放错类别，会让调用者难以发现或难以正确使用它。例如把 Prompt 做成 Tool，会使对话模板看起来像有副作用的执行操作；把需要复杂计算的 Tool 做成 Resource，则会掩盖输入参数和执行成本。

## 6. 插件边界上的风险意识

插件带来扩展性，也引入了边界风险。学习时应主动检查以下问题：

| 问题 | 为什么重要 |
| --- | --- |
| 输入参数是否在插件内再次验证 | 注册表只负责定位，不了解具体业务约束 |
| 外部访问是否会失败或超时 | 插件可能依赖文件系统、命令或网络 |
| 同名能力如何处理 | 避免调用落到不确定的插件 |
| 插件与主程序的二进制兼容性是否受控 | 跨动态库传递结构化对象依赖共同契约 |
| 卸载时是否先注销索引 | 防止悬空引用和无效调用 |

这些不是要求插件永远不会失败，而是要求失败能留在明确边界内，以统一结果或可观察错误的形式返回。

## 7. 学后自测

1. 为什么主程序不需要知道每个插件的具体业务实现？
2. 插件启动时登记的能力定义，与调用时产生的工具结果有什么区别？
3. 为什么 Resource 不能简单理解为“没有参数的 Tool”？
4. 为什么 Prompt 不应被理解为“自动执行工具”？
5. 为什么注销能力索引必须先于销毁插件实例？
6. 若一个新需求既能做成 Tool 又能做成 Prompt，应依据什么选择？
7. 参数校验为什么不能只依赖协议层？
