# 第 3 讲：两种传输方式与会话边界

> 学习目标：理解同一条 MCP 协议主干，如何被 stdio 和 HTTP+SSE 两种传输方式承载；重点区分请求 ID、SSE 会话 ID、HTTP 请求和真正的 MCP 响应。

第 2 讲故意把传输层压缩为“交付完整 JSON 文本”和“返回 JSON 响应文本”。本讲只把这两端展开。协议解析、方法路由和插件调用仍是同一条中段主干，不重复讨论。

## 这一讲要回答的问题

```text
连续字节流中，服务器怎样知道一条消息在哪里结束？
HTTP POST 已返回，为什么 MCP 响应还没有到客户端？
SSE 会话 ID 与 JSON-RPC 请求 ID 分别解决什么问题？
为什么 HTTP 模式需要队列，而 stdio 模式通常不需要？
```

## 1. 先抓住不变与变化

两种传输方式的共同核心不变：

```text
完整 JSON 请求文本
  -> 协议主干
  -> JSON 响应文本
```

变化只发生在两端：

| 维度 | stdio | HTTP+SSE |
| --- | --- | --- |
| 请求从哪里进入 | 标准输入的连续字节流 | HTTP POST 的请求体 |
| 如何确定消息边界 | 长度头给出后续消息体的字节数 | HTTP 已提供本次请求体边界 |
| 响应从哪里离开 | 标准输出 | 与请求分离的 SSE 长连接 |
| 返回是否同步可见 | 写入后立即在输出流中可读 | 先入会话队列，再异步推送 |
| 关联方式 | 请求 ID 主要用于协议匹配 | 请求 ID 匹配协议；会话 ID 找到正确的 SSE 流 |

不要把“stdio 与 HTTP+SSE”理解成两套 MCP 业务逻辑。它们是同一条协议流水线的两种外壳。

## 2. stdio：一条双向字节通道

stdio 模式常用于本地 MCP 客户端启动并管理服务器进程的场景。客户端和服务器通过一对标准输入输出流交换消息。

### A. 为什么需要长度边界

标准输入不是“一次读取恰好得到一条 JSON”的消息队列，而是连续字节流。若连续发送两条 JSON，接收方无法仅凭读取动作天然判断第一条在哪里结束。

因此每条 MCP 消息采用长度前缀形式：

```text
Content-Length: N\r\n
\r\n
恰好 N 个字节的 JSON 消息体
```

服务器的入站过程是：

```text
连续字节流
  -> 读取长度头
  -> 得到 N
  -> 精确读取 N 个字节
  -> 得到完整 JSON 请求文本
  -> 交给第 2 讲的协议主干
```

这里“精确读取”很重要：JSON 中可能包含换行、空格或任意字符，不能把“读到换行”误认为一条消息结束。真正的边界由长度头决定。

### B. stdio 的出站过程

第 2 讲产生 JSON 响应文本后，stdio 通道再次加上长度头，并写入标准输出：

```text
JSON 响应文本
  -> 计算字节数 N
  -> 组装长度头 + 空行 + 消息体
  -> 写入标准输出并立即刷新
  -> 客户端按同样规则读取
```

一次请求和对应响应都在这对进程流中交换。JSON-RPC 请求 ID 仍然负责让客户端在协议层知道“这个响应对应哪次请求”；它不是字节分帧工具。

## 3. HTTP+SSE：两条方向不同的通道

HTTP 模式把“客户端向服务器发请求”和“服务器向客户端推响应”拆开：

```text
POST /message：客户端 -> 服务器，提交 MCP JSON 请求

GET /sse：服务器 -> 客户端，保持长连接，推送 MCP JSON 响应
```

拆分的原因是普通 HTTP 请求响应模型不适合服务器在稍后、甚至多次主动推送消息；而 MCP 需要把异步结果可靠地送回对应客户端。

### A. 建立 SSE 会话

HTTP 客户端先发起 SSE 长连接。服务器为这条连接创建或恢复一个会话，并返回一个会话 ID 与可提交请求的地址信息。

此时会产生一份会话状态：

```text
会话 ID
  -> 一个待发送消息队列
  -> 一条仍然打开的 SSE 长连接
```

这份状态只回答“之后的服务器消息应推给哪个客户端连接”。它不解释某条 MCP 响应属于哪一个 JSON-RPC 请求，后者仍由请求 ID 解决。

### B. 提交 MCP 请求

客户端携带会话 ID 向消息端点发送 HTTP POST，请求体就是完整 JSON-RPC 请求文本：

```text
HTTP POST
  + 会话 ID
  + JSON 请求体
  -> 服务器确认会话存在
  -> 将请求体交给第 2 讲的协议主干
```

HTTP 本身已经确定了请求体边界，因此这个入口不再需要 `Content-Length` 风格的 MCP 帧头。

这个 POST 的即时响应是“已接收”，而不是 MCP 业务结果。它只表示服务器接受了这次 HTTP 投递，不能表示工具已经执行成功，也不能替代 JSON-RPC 响应。

### C. 响应如何异步回到 SSE 流

协议主干生成 JSON 响应文本后，HTTP 模式不会直接把它写回刚才的 POST 响应，而是按当前会话 ID 放入该会话的待发送队列：

```text
JSON 响应文本
  -> 按会话 ID 找到待发送队列
  -> 入队
  -> 唤醒 SSE 发送端
  -> 封装为 SSE message 事件
  -> 沿已打开的 SSE 连接推给客户端
```

队列使处理请求的 HTTP 工作和向浏览器写入长连接这两件事可以解耦：前者只需把结果交给会话，后者在连接可写时按顺序发送。

## 4. 两种 ID 解决不同问题

最常见的混淆，是以为会话 ID 能替代请求 ID，或反过来。它们处在不同层次。

| 标识 | 属于哪一层 | 回答的问题 | 生命周期 |
| --- | --- | --- | --- |
| 请求 ID | JSON-RPC 协议 | “这个 MCP 响应对应哪次 MCP 请求？” | 一次协议往返 |
| SSE 会话 ID | HTTP 传输 | “这条服务器消息该推到哪条客户端连接？” | 连接存活期间，可用于重连 |
| 聊天会话 ID | 对话状态 | “这些历史消息属于哪段对话？” | 多轮聊天期间，可被持久化 |

它们的实际配合是：

```text
会话 ID 把 POST 请求绑定到正确的 SSE 发送队列。
请求 ID 保留在 JSON-RPC 响应中，让客户端匹配具体的 MCP 请求。
聊天会话 ID 只在聊天路径中管理历史，不应被当作 MCP 请求 ID。
```

第 5 讲会专门展开聊天会话 ID；本讲只讨论前两者。

## 5. 以同一条 tools/call 对比两种传输

假设客户端提交的业务内容完全相同：调用一个已登记工具。

### stdio 下的时序

```text
客户端
  -> 标准输入：长度头 + JSON 请求文本
服务器
  -> 读到完整请求文本
  -> 协议主干：解析、路由、定位插件、执行
  -> 得到 JSON 响应文本
  -> 标准输出：长度头 + JSON 响应文本
客户端
  -> 根据请求 ID 匹配响应
```

### HTTP+SSE 下的时序

```text
客户端
  -> GET /sse：建立长连接，获得会话 ID
  -> POST /message：会话 ID + JSON 请求文本
服务器
  -> 返回“已接收”HTTP 确认
  -> 协议主干：解析、路由、定位插件、执行
  -> 得到 JSON 响应文本
  -> 按会话 ID 放进待发送队列
  -> SSE 推送 message 事件
客户端
  -> 从 SSE 收到 JSON 响应文本
  -> 根据请求 ID 匹配响应
```

二者在“协议主干”完全相同。HTTP+SSE 多出的工作是建立会话、将结果入队，以及把队列中的消息转换为 SSE 事件。

## 6. 连接中断与重新建立边界

传输层还需要处理一个现实问题：客户端连接不会永远保持。

在 stdio 中，标准输入结束通常意味着客户端或进程生命周期结束，服务器停止读取该流。

在 HTTP+SSE 中，SSE 连接可能断开后重新建立。客户端带回原会话 ID 时，服务器可以尝试恢复同一会话的发送目标；若请求提交时会话不存在，则服务器应拒绝该请求，而不是把响应送到一个未知连接。

这说明会话 ID 还有一个边界作用：它把“能否把结果送回”的传输问题显式化。即使协议请求完全合法，若没有可用的会话发送路径，客户端仍可能收不到响应。
