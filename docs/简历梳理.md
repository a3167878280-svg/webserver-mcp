## 一、项目全景（先建立整体认知，30 秒版）

TinyMCP 是一个 **MCP 服务器**——让 LLM（Claude / GPT 等）能通过**标准协议**调用你机器的真实能力（读文件、查天气、跑命令、查 B 站……）。LLM 本来只会聊天，MCP 是连接 LLM 和外部工具的"插座标准"。

一条 MCP 请求从进入到返回的完整链路：

```
客户端(浏览器/Claude Desktop)
   │  POST /message 或 stdin 输入
   ▼
[传输层]  原始字节 → JSON字符串        (stdio / HTTP+SSE，只负责搬运)
   ▼
[协议层]  parse → route → execute → serialize   (JSON-RPC 2.0)
   │        解析     路由     执行      序列化
   ▼
[插件层]  dlopen 加载的 .so，真正干活  (file / weather / bilibili ...)
   ▼
反方向原路返回响应
```

**关键设计：传输层和协议层解耦。** `src/main.cpp:90` 的 `on_message` 回调是统一的协议管道，两种传输复用同一个管道——stdio 模式只是"把 stdin 的字节流拼成完整 JSON 字符串，再写到 stdout"；HTTP+SSE 只是"从 POST body 拿 JSON，再把响应推到 SSE 流"。协议层完全不感知自己在哪种传输上。这是整个项目的骨架，讲任何一条前先把这个讲清楚。

## 二、第 1 条：JSON-RPC 2.0 四段管道 + 9 种方法 + 三大能力

**这条在做什么**：把"一条 MCP 请求从字符串变成业务结果再变回字符串"的全过程，拆成四个职责单一的阶段。

### 实现细节

1. **解析 Parse** — `src/mcp/jsonrpc_parser.cpp`：把原始 JSON 字符串 → `JsonRpcRequest` 结构体。校验：必须是合法 JSON → 必须是 Object → `jsonrpc` 必须等于 `"2.0"` → `method` 必须是字符串 → `params`/`id` 可选（`id` 为 null 表示 notification，无需回复）。校验失败返回 `nullopt`，上层发 **-32700 解析错误**。
2. **路由 Route** — `src/mcp/mcp_handler.cpp:37-65`：一张 `std::map<std::string, handler>` 路由表，method 字符串 → 处理函数指针（lambda）。找不到返回 **-32601 Method not found**。
3. **执行 Execute** — 每个 `handle_xxx()` 干具体事：`handle_tools_list` 遍历插件注册表收集工具、`handle_tools_call` 按名字分发到插件执行、`handle_resources_read` 按 URI 读资源……
4. **序列化 Serialize** — `src/mcp/jsonrpc_serializer.cpp`：`JsonRpcResponse` 结构体 → JSON 字符串，回显请求的 `id` 让客户端配对。

**9 种方法**：`initialize`（握手，声明协议版本 + 能力）`ping`（心跳）`tools/list` `tools/call` `resources/list` `resources/read` `prompts/list` `prompts/get` `notifications/initialized`（通知，id=null 不回复）。

### 三大能力的本质区别（面试必考）

- **Tools = 动词**：LLM 主动调函数 → 执行 → 返回结果。谁先发起？**LLM**。
- **Resources = 名词**：服务器被动声明"我有这些数据"（如 `config://server` 资源），客户端浏览列表 → 选一个读。谁先发起？**客户端/用户**。
- **Prompts = 模板**：预设对话模板，用户选模板 → 填参数 → 生成预设消息。

### 为什么这么设计

每段职责单一、可独立测试（单测就是对着 parser/serializer/handler 写的）；且管道是纯数据流，换传输层不影响协议层。

### 面试问答

- **"如何新增一个 MCP 方法？"** → 在 `register_handlers()` 往 `m_routes` 加一条 `method → lambda` 映射 + 写一个 `handle_xxx`。路由表驱动，parse/serialize/transport 一行都不用动。
- **"notification 怎么处理？"** → `handle()` 检测 `id==null` 返回 `nullopt`，`src/main.cpp:106` 收到空就不 `send`，客户端不期望回复。
- **"错误怎么统一？"** → 解析失败 -32700、方法不在表 -32601、handler 抛异常被 try/catch 包住转 **-32603**。错误码工厂方法集中在 parser 里。

## 三、第 2 条：双传输抽象（stdio / HTTP+SSE）

**这条在做什么**：同一套协议逻辑，支持两种连接方式——本地进程间（Claude Desktop 用 stdio 拉起）和远程 HTTP（浏览器页面用）。

### stdio 通道

**实现**（`src/transport/stdio_transport.cpp`）：MCP 的 stdio 帧格式是长度前缀协议：

```
Content-Length: 89\r\n
\r\n
{"jsonrpc":"2.0","id":1,"result":{...}}
```

- 读：`read_loop` 逐字节读直到遇到 `\r\n\r\n` 拿到头 → 提取 `Content-Length` 的 N → 精确读 N 字节得到完整消息体 → 回调交给 `on_message`。
- 写：拼 `Content-Length` 头 + body，`fwrite` 后立即 `fflush`（Claude Desktop 在管道另一端等数据）。

**为什么需要帧协议**：stdin/stdout 是**字节流**没有消息边界，不封帧会粘包/半包。加长度前缀解决。

### HTTP+SSE 通道

**为什么不能用单个 POST 返回结果**：HTTP 是"请求→响应"单向的，服务器**无法主动推送**；而 MCP 的 streamable HTTP 规范要求响应经 SSE 事件流异步到达。所以拆成双通道：

- **通道1 `GET /sse`**：SSE 长连接，服务器 → 客户端。httplib 的 chunked content provider 让 handler 常驻运行；连接建立后先发一条 `event: endpoint\ndata: /message?session_id=xxx`（告诉浏览器往哪发请求），然后进入"等待循环"。
- **通道2 `POST /message`**：客户端 → 服务器。收到 JSON-RPC 请求走 `on_message` 管道，但**不直接返回结果**，而是回 **HTTP 202 Accepted**——"请求收到了，结果走 SSE 给你"。

**多客户端隔离**（`src/transport/http_sse_transport.h:84-89`）：每个客户端 = 一个 `Session`（UUID 标识），内含独立的 `pending` 队列 + `condition_variable`。服务器维护 `map<session_id, Session>`。POST 线程（生产者）把响应 push 进队列 → `notify_one` 唤醒 SSE 线程（消费者）→ pop 出来推给浏览器。经典**生产者-消费者**模型。

**重连恢复**：`GET /sse?session_id=xxx` 时若 session 已存在就复用，不清空队列，之前没发完的消息继续发。

### 面试问答

- **"两种传输怎么共用一套逻辑？"** → 抽象 `Transport` 接口（`send()` + `set_on_message()`），`src/main.cpp:90` 的 `on_message` 是统一协议管道；传输层只负责"字节 ↔ JSON 字符串"，协议层不感知传输类型。
- **"SSE 里那个 500ms wait_for 是干嘛？"** → 队列空时条件变量会阻塞；`wait_for(500ms)` 是为了定期醒来检查 `m_running`，保证服务器 stop 时线程能退出。

### ⚠️ 需要准备的一题："多客户端并发时，响应怎么保证不错发？"

**诚实答案**：当前 `m_current_session_id`（`src/transport/http_sse_transport.h:109`）是**一个被 mutex 保护的共享变量，不是 `thread_local`**（注释却写着"线程局部"）。httplib 多线程并发处理 POST 时，两个不同 session 的请求可能互相覆盖，极端情况下响应会串线。设计意图是对的，但实现有边界。

**面试建议**：主动承认"这个边界我识别到了"，并说出修复方案（改成 `thread_local`，或把 session_id 顺着回调链传下去）。这比被问住强得多。

**建议投简历前修掉它**（改起来不到半小时）。

## 四、第 3 条：插件化架构（IPlugin + dlopen/dlsym）

**这条在做什么**：让主程序不 care 具体工具怎么实现，写一个 `.so` 丢进 `plugins/` 目录就能热插拔。

### 实现细节

接口契约（`src/plugin/plugin_interface.h`）：

- **必须实现**（纯虚）：`name()` / `version()` / `get_tools()` / `call_tool()`
- **可选覆盖**（带默认空实现）：`get_resources()` / `read_resource()` / `get_prompts()` / `get_prompt()`
- 这样只做 Tools 的插件（如 weather）不用写任何 Resources/Prompts 代码；能同时提供三类能力的插件（如 `FilePlugin`，文件工具 + `config://server` 资源 + `file_analyzer` prompt）按需重写。

每个 `.so` 必须导出两个 **`extern "C"`** 符号（`plugin_interface.h:138`）：

```cpp
extern "C" IPlugin* create_plugin();       // 工厂：new 一个插件实例
extern "C" void destroy_plugin(IPlugin* p); // delete
```

加载流程（`src/plugin/plugin_manager.cpp:110-158`）：

```
dlopen(path, RTLD_NOW)      → 立即解析所有符号（比 RTLD_LAZY 安全，缺失符号当场报错）
dlsym("create_plugin")      → 拿到工厂函数地址
dlsym("destroy_plugin")     → 拿到析构函数地址
create()                    → 得到 IPlugin* 实例
get_tools()                 → 把工具注册进全局 PluginRegistry
```

卸载顺序是**逆序**（后进先出），并反注册 → `destroy_plugin` → `dlclose`。

**为什么 `extern "C"`**：C++ 编译器会把函数名 mangling 成 `_Z13create_pluginv` 这种乱码，`dlsym` 是按字符串找符号的，`extern "C"` 保证符号名就是 `create_plugin`。

**跨 .so 的 ABI 安全**：插件和主程序必须用**相同版本的 GCC + C++17** 编译，这样 `std::string`/`std::vector`/`nlohmann::json`（header-only，两边是同一份代码）内存布局一致，跨边界传递才安全。

### 为什么这么设计

热插拔（加工具不重编主程序）、隔离（插件出错不拖垮主程序）、独立开发（约定接口即可并行开发）、按需加载（删 `.so` 即禁用）。5 个插件都是这种模式，验证了架构可扩展性。

### 面试问答

- **"为什么不直接静态编译进去？"** → 上面四条理由，突出"约定接口 → 独立编译 → 运行时加载"的解耦。
- **"新增一个插件要几步？"** → ① 继承 `IPlugin` 实现方法 ② 实现 `create_plugin`/`destroy_plugin` 两个 C 函数 ③ 写一个 `add_library(xxx SHARED)` 的 CMakeLists。主程序零改动。
- **"主程序怎么调用工具？"** → 只通过 `PluginRegistry`（按名查插件 → `call_tool`），`McpHandler` 只依赖 `IPlugin` 抽象和注册表，不 include 任何插件实现头文件。

## 五、第 4 条：LLM Agent 工具调用循环 + 上下文管理

**这条在做什么**：让 LLM 不只是"聊天"，而是能**自主决定调哪个工具、看结果、再决定下一步**，形成多轮推理循环。

### 核心流程（`src/llm/tool_orchestrator.cpp:86-284`，`process()`）

```
用户消息
  → 拼 messages = [system + 历史 + 用户新消息]
  → 内部调 tools/list 拿全部工具，过滤用户禁用的
  → while (round < 10):                    // 防死循环
  →     LLM 流式输出（delta 推给前端做打字效果）
  →     分支A: LLM 返回 tool_calls？
  →        逐个执行工具（走 MCP tools/call → 插件真实执行）
  →        把 assistant(工具调用) + tool(执行结果) 追加回 messages   ← 结果回填
  →        continue（带着结果再问 LLM）
  →     分支B: 无 tool_calls → LLM 给出最终回复 → 结束
```

**结果回填为什么是关键**：LLM 自己看不到工具执行结果，必须把 `tool` 角色的消息塞回 messages，下一轮 LLM 才能"基于事实"继续推理或给最终答案。这是 Agent 和纯 chat 的本质区别。

### 上下文管理（三层防线，防止上下文溢出）

1. **启发式 Token 估算**（`src/llm/context_manager.cpp`）：UTF-8 解码 + CJK 范围判定，CJK 每字符按 **1.0 token**、ASCII 按 **0.25 token** 估算；再按模型名前缀查预算表（gpt-4o/claude 100k~180k，qwen/llama 本地模型 28k…）。不是精确 tokenizer，但做截断/摘要的**判断依据**足够。
2. **长工具结果截断**：单个工具结果超过预算 **25%** 就截断（`truncate_tool_result`，按 token 预算从字符流裁剪，末尾追加 `[... truncated, original: N chars]` 标记）。
3. **历史摘要压缩**：messages 总量超过预算 **70%**（`HEADROOM_PCT`）→ 再调一次 LLM（**不带 tools**，轻量调用）把最旧的 **60%** 消息压成一条 `system` 摘要，替换掉原文。摘要失败有**降级方案**：手动拼前几条用户消息的前 80 字。

### 多厂商支持（`src/llm/llm_client.cpp`）

`base_url` 里含 `anthropic` → 走 Anthropic 消息格式（带 `anthropic-version` 头）；否则走 OpenAI 兼容格式（`Authorization: Bearer`）。兼容本地 OpenAI 兼容服务（Ollama / llama.cpp），流式带 tools 失败时降级非流式重试。`strip_think()` 负责剔除 Qwen3/DeepSeek 的 `<think>` 思考块，避免把思维过程当回答推给前端。

### 面试问答

- **"怎么防止死循环？"** → `MAX_ROUNDS = 10`（`src/llm/tool_orchestrator.h:127`），超限强制返回错误。
- **"工具结果太大怎么办？"** → 25% 预算截断 + 引导 LLM 总结（结果后附加"请基于以上数据给用户一个明确、直接的中文回答"）。
- **"摘要掉的是不是重要信息？"** → 摘要只压最旧 60%、至少保留最近 2 条；且摘要也是 LLM 生成的（带工具结果），关键事实在摘要里。
- **"token 估算为什么不直接用库？"** → 项目目标是**本地快速判断**（截断/摘要触发阈值），不需要精确到 tokenizer 级别，启发式 + 每模型预算表在成本/精度间平衡；这是**有意为之的取舍**，能讲清楚这个权衡本身就是加分项。

## 六、第 5 条：异步日志 + 对话持久化

**这条在做什么**：日志和对话落盘都是磁盘 IO，直接放请求路径会阻塞业务。用**生产者-消费者**解耦，一次基础设施服务两条写路径。

### 实现细节

阻塞队列（`src/log/block_queue.h`）：**环形数组** `m_back = (m_back + 1) % m_max_size`，固定容量复用，避免频繁分配；`mutex + 条件变量` 保证线程安全阻塞（`pop` 空时 `cond.wait` 睡眠）。

异步写路径（`src/log/log.cpp`）：

```
write_log(): 拼好日志字符串
  → if (异步模式 && 队列没满)   push 进队列（快，业务线程不碰磁盘）
  → else                        直接 fputs 到文件（队列满时降级同步写，保证不丢日志）
flush_log_thread(): 独立线程从队列 pop → 写文件
```

**按天切分 + 按行数切分**（`log.cpp:111-132`）：发现 `m_today != 今天的日` 就关旧文件、打开 `2026_08_03_ServerLog` 新文件；同一日内还会按行数（`m_count % m_split_lines`）再切，防止单文件无限膨胀。

**对话持久化复用同一套基础设施**（`src/server/conversation_manager.cpp:132-147`）：`save_to_file()` 把完整对话 JSON 拼成 `file_path + '\n' + content`，调用 `Log::persist()` 塞进**同一个持久化队列**，由 `persist_thread` 异步落盘；队列满同样降级同步写。**不再为每个会话开 `std::ofstream` 同步写**——一个 block_queue + 独立线程，服务日志和对话两条路径，这是这条设计的点睛之处。读路径：构造时 `load_all()` 扫描 `logs/` 目录恢复内存态。

### 为什么这么设计

写日志/落盘是慢 IO，放进业务线程会拖慢请求；异步化让业务线程只做"入队"这种纳秒级操作。而"队列满降级同步写"是**可靠性优先的兜底**——宁可慢，不丢数据。

### 面试问答

- **"环形队列相比 std::queue 的好处？"** → 固定容量数组 + 循环下标，无频繁扩容/内存分配；O(1) 入队出队。
- **"队列满了为什么降级同步而不是丢日志？"** → 日志的语义是"尽量不丢"，性能可以让步；这是明确的设计取舍。
- **"为什么对话落盘复用日志系统？"** → 避免重复造异步写盘轮子，一个队列 + 一个线程服务两类消费者；职责内聚、代码量小。

## 七、第 6 条：CMake 构建 + 5 个插件子项目 + 测试/基准

**这条在做什么**：一个主程序 + 5 个独立 `.so`，一套构建搞定，还挂了单测和压测。

### 实现细节（`CMakeLists.txt`）

- `project(TinyWebServer-MCP VERSION 0.1.0)`，`CMAKE_CXX_STANDARD 17`。
- **一个可执行 `mcp_server`**（全部 src 源文件）+ **`add_subdirectory` × 5**（file / weather / review / bilibili / command），每个插件 `add_library(xxx SHARED)` 编译成 `.so`，通过 `set_target_properties(LIBRARY_OUTPUT_DIRECTORY ...)` 统一输出到 `build/plugins/`。
- **依赖**：`pthread`、`${CMAKE_DL_LIBS}`（= dl，dlopen 用）、`stdc++fs`（filesystem）、`ssl` + `crypto`（OpenSSL，配合宏 `CPPHTTPLIB_OPENSSL_SUPPORT` 启用 httplib 的 HTTPS 能力）。
- 第三方库 **vendor 进 `third_party/`**：`httplib.h`、`nlohmann/json.hpp`，不依赖系统安装。

**关键设计——插件如何独立于主程序**：插件 target 只 `include_directories(src + third_party)`、只链 `dl + stdc++fs`，**不链接主程序可执行文件**；编译期完全解耦，运行期靠 dlopen 拉起来。契约只在 `plugin_interface.h` 这一个头文件里。

### 测试与基准（`BUILD_TESTING` 门控，`ctest` 一键跑）

- `mcp_core_tests`：自研轻量断言框架，覆盖——parser（合法 JSON-RPC 通过、非法 JSON 拒绝、错误协议版本 `1.0` 拒绝）、serializer（成功响应输出格式）、路由分发（tools/list、tools/call 按名分发到持有插件、resources/read、prompts/get）、未知方法返回 **-32601**、**notification 不产生响应**。
- `mcp_core_benchmark`：核心路径（parse → route → serialize）压测程序，`build-bench/` 已有构建产物。

### 面试问答

- **"为什么第三方库 vendor 而不走包管理器？"** → httplib/nlohmann 都是 header-only，vendor 进来构建零网络依赖、版本锁定、跨机器可复现；项目当前没有用 vcpkg/conan 的必要。
- **"插件为什么不在主程序 target 里？"** → 编译期解耦 + 运行期加载是整套插件架构的根基，CMake 侧用独立 SHARED target 体现同一思想。
- **"基准测了什么、多少量级？"** → 建议跑一次 `build-bench/mcp_core_benchmark`，把数字记下来（比如"单条请求 parse→route→serialize 全程 X 微秒、单线程压测 Y req/s"），面试时直接报数，比"性能还不错"有说服力得多。

## 八、全局"一页纸项目故事"（60 秒开场白）

> "我做了一个基于 C++17 的 MCP 协议服务器。MCP 是让 LLM 调用外部工具的标准协议，我的服务器就是协议的一端。核心架构分三层：**传输层**支持两种——stdio 是本地进程通信、用 Content-Length 帧协议；HTTP+SSE 是远程浏览器通信，用 GET /sse 长连接 + POST /message 双通道、session 队列做多客户端隔离。**协议层**是 JSON-RPC 2.0 的四段管道，解析→路由→执行→序列化，覆盖 Tools/Resources/Prompts 三大能力的 9 种方法。**插件层**用 dlopen 动态加载 .so，5 个插件只依赖一个 IPlugin 接口，热插拔。在这之上我还做了两层工程增强：一是 LLM Agent 工具调用循环，让 LLM 能自主决定调工具、看结果、多轮推理，配套 token 估算、结果截断和摘要压缩防上下文溢出；二是异步日志系统，环形队列 + 独立线程刷盘，队列满降级同步写保证不丢，这套基础设施还复用了对话持久化。最后用 CMake 统一构建主程序和 5 个插件，配了 CTest 单测和核心路径压测。"

每句话对应简历一条，且每一句背后都能往下挖一层（上面各条的"面试问答"就是挖掘路径）。
