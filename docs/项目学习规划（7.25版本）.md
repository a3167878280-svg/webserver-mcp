# TinyMCP 项目学习规划（7.25版本）

## 0. 先建立整体目标

TinyMCP 的目标不是做一个聊天网页，而是做一台可以被 AI 客户端使用的“能力服务器”。它把本机或网络中的实际能力，例如读文件、查询天气、执行命令、审查代码，组织成统一的可发现、可调用、可返回结果的服务。

从使用者视角，系统解决的是下面这件事：

```text
AI 客户端或聊天用户提出意图
        ↓
系统知道有哪些能力可用，并把需要执行的能力交给对应实现
        ↓
把执行结果以客户端能识别的统一格式返回
```

这里有两层职责，必须分开理解：

- MCP 层负责把能力以标准协议提供出去。它并不判断“该不该调用天气”，只接收已经明确的请求并完成分发。
- 聊天层负责与大模型协作。它把用户自然语言、历史消息和工具描述交给模型；模型决定是否以及如何调用能力。

所以，项目的核心价值可以概括为：**让异构能力以统一接口暴露给 MCP 客户端，也让大模型能在对话中按需使用这些能力。**

## 1. 运行时有哪些角色

先不看实现细节，只识别运行时谁在和谁说话、各自持有什么数据。

| 角色 | 负责什么 | 主要持有或传递的数据 |
| --- | --- | --- |
| MCP 客户端 | 直接发现并调用服务器能力 | 协议请求、请求标识、参数、响应 |
| 聊天前端 | 接收用户输入，展示流式回答和工具状态 | 用户消息、会话标识、模型连接信息、流式事件 |
| 传输通道 | 让消息进出服务器 | 字节流、HTTP 请求体、SSE 事件、会话标识 |
| 协议处理中心 | 校验消息形状，按方法名选择业务动作 | 结构化请求、结果或错误、通知状态 |
| 插件目录与加载器 | 在服务器启动时发现并装载能力模块 | 插件库、插件实例、生命周期信息 |
| 能力注册表 | 从“能力名称或资源标识”快速找到所属插件 | 工具/资源/提示模板的索引 |
| 插件 | 真正执行文件、命令、天气、审查等具体工作 | 调用参数、业务结果、失败说明 |
| LLM 服务 | 根据对话决定回答或请求工具调用 | 消息历史、工具清单、工具调用意图、文本增量 |
| 对话存储 | 在需要时保存和恢复一段对话 | 会话 ID、用户消息、助手回复、工具结果 |

两类重要标识贯穿运行时：

```text
请求 ID：把一条协议响应对应回原始协议请求。
会话 ID：把同一个浏览器连接、流式事件和可选的对话历史关联起来。
```

它们不能混为一谈。请求 ID 面向一次 MCP 往返；会话 ID 面向一个持续连接或多轮聊天上下文。

## 2. 两条请求路径

项目有两条业务意义不同的路径：

```text
路径一：MCP 客户端直接请求能力
路径二：聊天用户请求回答，LLM 决定是否使用能力
```

路径一的入口有两种传输变体：本地标准输入输出，或 HTTP 发送请求加 SSE 接收结果。这只改变消息如何抵达和离开服务器，不改变中段的协议处理与插件分发。

路径二是 HTTP 聊天接口。它不是另一套插件系统，而是先让 LLM 做推理和决策；当模型要求工具时，再回到路径一中“按名称分发能力”的同一条主干。

### 2.1 路径一：MCP 客户端直接请求能力

适用场景：桌面 MCP 客户端、IDE、自动化程序等已经知道自己要做什么，例如列出工具、读取资源、取得提示模板或调用某个工具。

#### A. 消息进入

客户端先构造一个协议请求。它包含三类核心信息：

```text
method：要执行的协议动作，例如“列出工具”或“调用工具”
params：该动作需要的数据，例如工具名称和工具参数
id：本次请求的关联标识；没有 id 的消息是通知，不期待响应
```

消息有两种进入方式：

```text
stdio：长度头 + JSON 消息体，经标准输入进入。
HTTP+SSE：客户端先建立 SSE 接收通道，再用 HTTP POST 提交 JSON 消息体。
```

此阶段的数据变化是：**未分帧的字节或 HTTP body，变成一段完整的 JSON 文本；HTTP 模式还会把这段文本关联到当前会话 ID。**

#### B. 协议理解与路由

服务器把 JSON 文本转成结构化协议请求，并检查它是否满足基本约束。随后根据 `method` 选择对应业务分支。

```text
JSON 文本
  -> 结构化请求 { 协议版本, id, method, params }
  -> 某个 MCP 业务动作
```

这里产生三种结果：

- 文本无法解析或请求不合法：生成协议错误结果。
- 方法不存在或参数无法满足业务要求：生成协议错误结果。
- 方法合法：继续进入“列举能力”“调用能力”“读取资源”或“取得提示模板”等分支。

通知是一个特殊分支：业务动作仍会被处理，但最终不生成响应数据。

#### C. 能力发现或执行

如果请求是列举类请求，注册表返回当前已加载插件公开的元数据：工具名称、说明、参数结构，或资源和提示模板的描述。

如果请求是执行类请求，数据流是：

```text
{ 能力名称, 参数 }
  -> 注册表按名称或 URI 查找
  -> 找到拥有该能力的插件
  -> 插件接收参数并执行实际工作
  -> 返回标准业务结果 { 内容, 是否失败 }
```

此时，外部请求的通用参数变成了插件能够理解的业务参数；插件的原始执行结果又被包裹为统一业务结果。插件报错不是进程崩溃，而应该成为可传递的失败结果。

#### D. 返回客户端

成功结果或错误结果会重新包装为协议响应，并回显原始请求 ID：

```text
业务结果 / 协议错误
  -> JSON 协议响应
  -> stdio 的长度帧，或目标会话的 SSE 消息
  -> 客户端
```

HTTP+SSE 模式下，POST 表示“服务器已接收请求”，真正的协议响应稍后从对应会话的 SSE 流送出。因此，同一次业务请求的入站和出站在 HTTP 层并不是同一条连接，但由会话 ID 关联。

### 2.2 路径二：聊天用户请求回答，LLM 决定是否使用能力

适用场景：用户输入自然语言，例如“帮我看看这个目录有什么问题”或“北京天气如何”。用户不需要知道工具名称、参数形式或插件归属。

#### A. 聊天请求与上下文准备

聊天前端提交用户消息，以及模型连接配置、可选会话 ID、历史消息和禁用工具列表。

服务器完成以下数据准备：

```text
用户输入
  + 既有历史（若存在）
  + 系统行为约束
  + 当前可用工具清单（可剔除被禁用项）
  -> 发给 LLM 的消息上下文与工具描述
```

如果提供会话 ID，用户消息会先进入该会话的历史；如果处于不保留历史的模式，则本次对话从更轻的上下文开始。

#### B. LLM 的第一次决定

LLM 返回的不是只有“最终文本”这一种数据，而有两种可能：

```text
情况 1：文本增量，没有工具意图
情况 2：文本增量 + 一个或多个工具调用意图
```

文本增量会立刻以 SSE 事件推给聊天前端，形成流式显示。工具调用意图包含工具名称和参数文本，但此时业务工具还没有真正执行。

#### C. 工具循环

若模型要求工具，系统把工具参数转换为结构化数据，再以内部分发请求的方式进入路径一的“能力执行”主干：

```text
LLM 工具意图
  -> { 工具名称, 参数 }
  -> 注册表定位插件
  -> 插件执行
  -> 工具结果
  -> 作为 tool 消息追加到 LLM 上下文
  -> 再次请求 LLM
```

这是一段循环，而不是单次调用。模型拿到工具结果后可能直接给出最终答案，也可能继续请求别的工具。为避免无限循环，系统有轮数上限；为避免工具输出挤占上下文，也会对过长的结果做控制或压缩。

前端在循环期间会收到不同类型的事件：文本增量、工具开始、工具结果、完成或错误。对话存储则在合适时机保存用户消息、工具结果和最终助手回复。

#### D. 最终回答

当 LLM 不再要求工具时，它输出的最终文本成为本轮聊天结果：

```text
最终文本
  -> SSE 的完成事件
  -> 聊天界面显示
  -> 可选写入会话历史
```

这一条路径最重要的边界是：**LLM 决定“调用什么”，插件负责“怎么执行”，协议主干负责“怎样可靠地分发和包装”。**

## 3. 插件如何工作

插件是能力的独立提供者。主程序不需要预先写死“天气如何查询”或“文件如何读取”；它只认识一份统一契约，并在启动时装入符合契约的插件。

### 3.1 启动阶段：从插件库到可发现能力

服务器启动时扫描配置的插件目录，找到动态库并依次装载。每个成功装载的插件会产生一个插件实例，然后上报自己提供的三类能力：

```text
Tools：可执行动作，需要名称与参数。
Resources：可读取的数据，通过 URI 标识。
Prompts：可复用的对话模板，需要名称与填充参数。
```

注册表把这些声明拆成三张逻辑索引：

```text
工具名       -> 插件实例 + 工具描述
资源 URI     -> 插件实例 + 资源描述
提示模板名   -> 插件实例 + 模板描述
```

因此，客户端先拿到的是“能力目录”，而不是插件内部实现；真正调用时才按照名称或 URI 找回对应插件。

### 3.2 请求阶段：从通用调用到具体业务

当收到工具、资源或提示模板请求时，注册表执行一次查表：

```text
客户端给出的名称或 URI
  -> 注册表定位唯一插件
  -> 插件执行自己的领域逻辑
  -> 返回统一结构
```

统一结构非常关键。无论底层是访问文件系统、发起网络请求、启动命令还是分析代码，调用者看到的都是同一种“内容数组 + 成功/失败状态”或相应的资源/提示模板结果。这样新增插件不会迫使协议层、聊天层或前端为每种能力改造一遍。

同名工具、同 URI 资源或同名提示模板会产生冲突。运行时应明确谁先注册、谁被保留，避免一次调用被不确定地分发给不同插件。

### 3.3 生命周期：装载、使用、卸载

插件的生命周期可记为：

```text
动态库文件
  -> 装载
  -> 创建插件实例
  -> 注册能力索引
  -> 接收多次调用
  -> 注销能力索引
  -> 销毁实例
  -> 卸载动态库
```

注销必须先于销毁。否则注册表仍持有已失效插件的引用，后续请求可能进入无效对象。

### 3.4 用三类能力建立正确直觉

| 能力类型 | 谁发起 | 输入 | 输出 | 适合什么 |
| --- | --- | --- | --- | --- |
| Tool | MCP 客户端或 LLM | 名称和参数 | 执行结果 | 查询、读取、修改、命令等动作 |
| Resource | 客户端浏览后读取 | URI | 数据内容 | 预先可发现的静态或半静态数据 |
| Prompt | 用户选择模板 | 模板参数 | 预设消息 | 让对话以稳定方式开始 |

不要把 Resource 当成无参数 Tool，也不要把 Prompt 当成会自动执行的 Tool。三者共用插件和注册表，但交互语义不同。

## 4. 后续学习节奏

目标是每讲结束后都能用自己的话复述一次数据流，而不是只记住名词。

### 第 1 讲：项目地图与启动前状态（30 分钟）

目标：明确系统启动后会得到哪些长期存在的对象和索引。

产出：画出“配置 -> 插件装载 -> 能力目录 -> 等待请求”的图，并列出配置、插件实例、能力索引、会话历史分别在哪个阶段产生。

### 第 2 讲：直接 MCP 请求的一次往返（45 分钟）

目标：用一次“列出工具”和一次“调用工具”跟完整数据变化。

产出：分别画出成功、未知方法、未知工具、通知四种结果如何离开服务器。

### 第 3 讲：两种传输方式与会话边界（35 分钟）

目标：理解 stdio 为什么需要长度边界，HTTP+SSE 为什么需要两条通道与会话 ID。

产出：写出同一个协议响应在 stdio 和 HTTP+SSE 下各自经历的封装形式。

### 第 4 讲：插件的契约与三类能力（45 分钟）

目标：明确插件如何声明能力、注册表如何定位插件，以及 Tool/Resource/Prompt 的职责差异。

产出：设计一个假想插件，写出它应暴露的能力目录和每类输入输出，不写代码。

### 第 5 讲：聊天与工具循环（60 分钟）

目标：理解自然语言请求如何变成 LLM 的工具意图，并重新接入插件主干。

产出：画出“无需工具”和“调用两次工具后回答”两条时序图，标记哪些消息需要进入历史。

### 第 6 讲：错误、边界与可靠性（45 分钟）

目标：从失败路径理解系统边界。

产出：列出至少六种失败情形，包括协议格式错误、方法不存在、能力不存在、插件业务失败、LLM 连接失败、SSE 会话断开，并说明调用方会看到什么数据。

### 第 7 讲：回到代码验证模型（按需）

目标：再将前六讲的抽象图逐块映射到具体模块、测试和日志。

产出：每个模块只回答四件事：输入是什么、输出是什么、它依赖谁、异常往哪里去。此时再阅读具体函数和文件，速度会明显更快，也不容易陷入局部细节。

## 5. 建议的学习方法

每一讲都采用同一个闭环：

```text
先画流程图
  -> 再挑一个真实请求验证图
  -> 记录输入、状态变化、输出和异常
  -> 最后才阅读实现细节
```

建议维护一张“运行时词汇表”，至少包含：请求 ID、会话 ID、JSON-RPC 请求、协议响应、工具定义、工具结果、资源 URI、提示模板、消息历史、流式事件。只要这些名词的生产者、消费者和生命周期都能说清，整个项目的骨架就已经掌握。
